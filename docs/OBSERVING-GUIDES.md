# 观测指南：设置与使用

[中文](OBSERVING-GUIDES.md) | [English](OBSERVING-GUIDES.en.md)

观测指南将人工收录与两个固定天象周刊合并展示，按来源发布时间倒序排列。它复用本站已有的公开文章，不单独采集、不调用模型，也不要求文章进入新闻“精选”。首次部署显示空列表不一定是故障。

## 1. 默认状态与收录范围

- `OBSERVING_GUIDES_AUTO_START_AT` 留空时，自动收录关闭，仅显示配置的人工条目。
- GitHub 公开版的人工名单为空，不携带运营站点文章或私有文章 ID。私有部署可能有自己的人工名单，不应复制别站 ID。
- 自动收录限于下列两个来源与系列；来源名、原始标题、官方 URL，以及 S&T 的 RSS 栏目标签共同决定是否匹配。来源名中的全角括号管理说明会被忽略，S&T 栏目标签不区分大小写。

| 来源（不含管理说明） | 自动栏目 | 随包来源 ID |
| --- | --- | --- |
| Astronomy Magazine · News | The Sky This Week | `rss-journal-astronomy-magazine` |
| Sky & Telescope · 天文新闻 | This Week's Sky at a Glance | `rss-journal-sky-telescope` |

另一个独立来源 `rss-journal-astronomy-sky-this-week` 不在这条自动规则内；只启用它不能替代上表的 Astronomy News 来源。泛 Observing 栏目、其他科普文章也不会仅凭中文标题关键词自动进入指南。

## 2. 配置自动收录

在 API 进程实际加载的环境中设置一个**固定的 UTC 启用时刻**：

```dotenv
OBSERVING_GUIDES_AUTO_START_AT=2026-10-23T10:00:00Z
```

上面只是格式示例，请替换为自己的启用时刻。当前校验要求 `YYYY-MM-DDTHH:mm:ssZ` 或带三位毫秒的 UTC `Z` 格式；不要填北京时间字符串、`+08:00`、单独日期或 `now`。不要在每次重启时重算为当前时间，否则收录边界会不断后移。

这不是文章发布日期门槛，而是本站文章的 `discovered_at` 入库边界：自动条目须在边界时刻或之后被本站发现，且不是历史回填条目。设置较早的边界可以纳入已存在、符合条件的记录，但不会主动重新采集历史。人工条目不受该自动启用边界限制。

然后按以下顺序配置：

1. 首次启动仍关闭采集、模型调用和推送，按[部署指南](DEPLOYMENT.md)完成基础检查。不要假定所有发行模板或私有部署使用相同开关默认值。
2. 在来源管理中核查并启用上表两个来源，保留来源身份与栏目证据；先完成相应用途的[版权与权限核查](CONTENT-RIGHTS.md)。
3. 配好模型、预算和容量后，才按自己的授权开启普通新闻采集与处理。正常采集通常需要 `COLLECT_ENABLED=true`，模型处理需要 `MODEL_CALLS_ENABLED=true`。**开启全局采集会影响所有已启用来源，不只这两个周刊。**
4. 更新环境后重新创建受影响的应用容器，或重启加载该环境的原生进程。API 必须读到启用时间；普通采集/分析开关也要作用于 worker。仅修改 `.env` 文件、仅重启 Web，或执行不刷新环境的 `docker compose restart` 都不足以应用新环境。已有业务先按升级流程排空在途付费请求。

自动指南读取本身不依赖 `MODEL_CALLS_ENABLED`；上述模型开关服务于上游新闻处理。已有公开合格文章无需为了加入指南再次分析。

## 3. 阅读、排序与人工条目

从首页天象日历卡的“观测指南”入口，或直接访问 `/observing-guides`。

- 人工与自动条目按文章身份去重后统一排序：来源发布时间最新的在上，无发布时间的在后；相同时间按稳定身份排序。
- 每页最多 30 条，有后续内容时显示“下一页”。游标是翻页位置标记，不需要手工编辑或保存到配置中。
- 点击文章卡片进入本站详情，再按原文链接阅读；原站可能需要登录或订阅。国外周报日期不是本站计算的本地可观测时间，仍需结合地点、时区、天气与星图判断。
- “未入选新闻精选”、较低 AI 分数或“图像与科普”分类本身，不会阻止符合规则的公开周刊进入观测指南。

若要人工加入其他指南，先确认文章已在**自己的部署**公开可读，再将其公开详情 ID 加入 `apps/web/app/features/observing-guides/guides.ts` 的 `OBSERVING_GUIDE_IDS`，重新构建和发布 Web。人工 ID 最多 20 个；手工名单并非后台环境开关，修改 `.env` 不会替代源码名单更新。不要把某个部署的文章 ID 提交到通用公开发行版。

## 4. 发布时避免旧构建覆盖

源码更新、编译产物更新和运行容器更新是三个步骤。源码已有新功能，不代表正在运行的 Web 使用了它。

- 按固定提交重新构建。参考 Dockerfile 会执行 `npm run build -w @aihot/web`，不要用旧的 `apps/web/build` 覆盖它。
- 原生部署也必须在目标源码上构建 Web，并重启实际提供服务的进程。
- 替换整套 Web 编译产物会影响所有页面，不能只验收本次修改的一个页面；至少回归观测指南自动列表、倒序和已有分页功能。
- 按[升级与回滚](DEPLOYMENT.md#7-升级与回滚)保留旧版本并核对实际运行镜像；不要为更新展示而清库、重新 seed 或重跑文章分析。

## 5. 最小验收与排查

1. 访问 `/api/site/observing-guides`：不传 `ids` 时，只检查自动收录结果。
2. 对照 `/observing-guides`：页面还会合并配置的人工 ID，因此它的条目数可以多于上面的自动接口。需要精确对照时，给接口传同一人工名单，例如 `?ids=YOUR_ARTICLE_ID`。
3. 找一篇启用边界后正常发现的批准周刊，确认新闻处理完成、已存在公开 publication、来源处于 editorial 参与模式，且已满足发布时间释放条件。排队、未知回执或“job completed”不等于文章已公开。
4. 对照页面与接口的文章身份、发布时间顺序，确认无重复，点击详情可达。超过 30 条时再检查真实下一页。

| 现象 | 先核查 |
| --- | --- |
| 首次部署为空 | 人工名单为空、自动边界未配置、来源未启用，或尚无公开合格文章 |
| 文章已采集但未出现 | 新闻处理/发布状态、来源身份、栏目证据、入库边界与 backfill 标记；不要直接重跑模型 |
| 接口有新文，网页仍是旧名单或旧顺序 | 正式 Web 的编译产物与运行镜像是否更新，而不是只看 Git 分支 |
| 文章持续等待 | 见[已知问题](../KNOWN-ISSUES.md)中的模型容量、超时与未知请求保护；不要无条件释放未知请求或扩大重试 |
| 手工修改翻页链接后出错 | 去掉 `cursor` 返回第一页。当前接口拒绝无效游标并返回 400；Web 对该错误的处理仍可能显示 500，属于独立已知限制 |

本说明依据当前读取层和构建配置整理，不替代某个新环境的实际安装验收。启用来源和模型可能产生外部请求与费用；检查指南页面本身不会为指南发起新采集或模型分析。
